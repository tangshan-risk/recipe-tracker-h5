## 第一阶段：想法起源（2026-10-17）

### 用户原始想法（语音转文字）

> "我还想到一个需求，就是像我这样的胖子，不是得做体重管理嘛，然后就得登记自己吃了什么。但是现在的APP都做得不好，拍了张照片，其实不能有效地识别出来那是一个什么东西，也不好计算那个热量。但是，手输吃了什么的话就太麻烦了，我觉得如果我们能拿大模型手搓出来一个APP，这个APP上传照片就可以识别出来吃了什么和热量，那应该很厉害"

> "这个是不是有了？而且，我觉得甚至都可以做成专门包大厂用的，因为大厂有食堂，到时候找个人给点钱，让他把那个今天的菜单传上来，或者就是用哪个用户传菜单就可以抽奖，或者有点小激励，然后拿那个菜单再去匹配和校准识别出来的那个菜到底是什么，我觉得就会很准。而且，菜单这种事情，他又不涉密，就也没关系。这样的话，肯定比一般的那种图片识别要准得多"

> "是有了，但是图片识别的效果并不好，不管是那个识别出来，它那个份量和热量其实都不太准。我觉得这个可以做的亮点就是食堂菜单校准"

> "有个点，大家更关心的是食堂吃饭热量，还是出去吃饭热量？这个我不知道，因为我从来没有在乎过，哈哈哈。都关心"

> "你说的这个需求，我确实看到好多人都有。我昨天看了半天小红书。但是有食堂的大多数时候是天天吃食堂"

### AI 初步分析

- 用户核心痛点：AI 拍照识别不准 + 手动输入太麻烦
- 差异化亮点：**食堂菜单校准**（将开放式识别转化为封闭集合匹配）
- 目标用户：天天吃大厂食堂、想减肥但嫌麻烦的男生
- 初步技术架构：Flask 后端 + H5 前端 + 通义 VL 视觉模型
- 创建技术验证 Demo：`caicaizhunzhun_demo.py`（对比开放式识别 vs 菜单封闭匹配的准确率差异）

## 第三阶段：产品需求明确（2026-10-18）

### 用户第一轮需求描述（语音转文字）

> "帮我梳理一版非常详细的会话记录，将我向你表达的内容和你的回复都整理到这个md文档中，然后也提交到github上"

（注：此处实为一段长语音，内容为 APP 的界面设计描述）

核心内容整理：
- **首页**：搜索框 + 拍照 icon + 趋势图标 + 热量缺口仪表盘 + 早/午/晚餐/加餐选项卡 + 今日食谱/饮食分析底部导航
- **添加界面**：日期时间 + 搜索框 + 常用/收藏/组合餐/自定义 + 食物分类浏览（豆类/坚果/零食饮料/肉蛋奶/蔬菜水果/主食/营养补剂）+ 食物卡片（图片+名称+热量+添加按钮）+ 已记录/完成打卡底部栏
- **已记录界面**：点击已添加按钮进入，显示选中的食物
- **技术栈倾向**：Flask + Python 后端，前端"按最稳健的去选择"

### AI 开始头脑风暴（brainstorming skill）

按照 brainstorming skill 流程，先确认理解，然后问一个能帮用户描述更多细节的问题。

### 用户回答（关键洞察）

> "是因为他拍照识别的东西不准，而且一般。嗯，作为男生在食堂吃饭，然后去记录这些东西，会有一点点的羞耻感，所以那个如果不是添加的很快，嗯，就会觉得很麻烦，所以希望就是通过这个 APP 能够让用户啊拍一张照片，然后就能非常好的识别到自己到底吃了什么东西，然后对应的是多少大卡去指导他。呃，记录自己的饮食，然后基于饮食去给出一些良好的建议啊，以及那个减肥的指导。"

**AI 总结出的三个真实痛点：**
1. AI 拍照识别不准（红烧肉→红烧排骨→红烧牛肉傻傻分不清楚）
2. 男生在食堂打饭有"拍照羞耻感"（不想被同事侧目）
3. 手动添加太麻烦（超过10秒就会放弃）

## 第四阶段：产品定位澄清

### AI 确认产品定位

> "菜菜准准"（暂定名）——以"拍照+菜单校准"为核心壁垒的饮食热量记录 H5 应用

### 用户纠正产品定位

> "我觉得不要在乎他是有菜单还是没有菜单的，然后我们可以有两个功能，一个功能核心的功能还是说添加食物，然后去记录自己吃了什么，这样保证这 APP 的一个通用性，但是，就我个人的体感而言，现在的那个 AI 拍照并不是特别的准，所以这个时候我们可以有另外一个入口，是让用户啊去上传那个呃，食堂的菜单……菜单是增强项，不是那个咱们这个 APP 的主体的功能"

**关键澄清：**
- **主体功能**：通用食物记录（任何场景都能用）
- **菜单校准**：可选增强项（有菜单时准确率翻倍）
- 菜单 = 开关，不是前置条件

### 用户指定技术栈

> "我打算先做 H5 的。圆形验证技术站可以考虑用 Flask 加 Python 的呃作为后台的主流语言，然后前端的话按照呃最稳健的健壮的去选择吧。这个我没有具体的要求，然后，我们在正式开发之前可以先考虑出一个，呃，需求规格说明书，然后在需求规格说明书确认完了之后，咱们再考虑做原型。"

**已确认：**
- 平台：H5（Web）
- 后端：Flask + Python
- 前端：用户无偏好，推荐 React + Vite + TailwindCSS
- 流程：先写 SRS → 确认 → 原型 → 开发

### 原型图分析结果（与v1.0 SRS对比）

**原型图 1 — 首页（饮食记录）**
| 项目 | v1.0 脑补 | 原型真实 |
|------|----------|---------|
| 仪表盘 | 圆环 | 半圆（汽车仪表盘样式，带刻度红黄绿+指针） |
| 数据展示 | 一个热量缺口数字 | **双卡片**：总消耗 891/2543 + 总摄入 0/1856 |
| 时段建议 | 固定值 | **区间值**（早餐 445~650、午餐 538~742） |
| 主题 | 没考虑 | **深色主题**（全程黑灰背景+白字+绿色强调） |
| TabBar | 今日食谱/饮食分析 | 一样，但**两个都标"会员"**（付费墙） |

**原型图 2 — 添加食物页（快速录入）**
| 项目 | v1.0 脑补 | 原型真实 |
|------|----------|---------|
| 导航布局 | 顶部横向滚动 | **左侧垂直导航**（常用/收藏/组合餐/自定义 + 食物分类） |
| 顶部Tab | 常用/收藏/组合餐/自定义 | 常用/收藏/**复制记录** |
| 食物格式 | "面包 188千卡 每小个" | "葱油饼 378千卡/150克" |
| 底部栏左 | "✅ 已选3项" | **"🍽️ 已记录"** |

**原型图 3 — 已记录弹窗**
| 项目 | v1.0 脑补 | 原型真实 |
|------|----------|---------|
| 加餐 | 一个 Tab | **三个 Tab**（上午加餐/下午加餐/晚上加餐） |
| 形态 | 独立页面 | **底部弹出模态框** |

**原型图 4 — 拍照引导页**
| 项目 | v1.0 脑补 | 原型真实 |
|------|----------|---------|
| 入口 | 直接进相机 | **单独引导页**（插图+说明文字+"开始拍摄"按钮） |
| 功能 | 只识别菜肴 | 支持**营养成分表**和菜肴两种（比我想的强！） |

**原型图 5 — 份量选择弹窗（🔥最震撼的差异）**
| 项目 | v1.0 脑补 | 原型真实 |
|------|----------|---------|
| 份量模型 | 小/中/大份（0.5x/1.0x/1.5x倍数） | **5档绝对热量值**（575/600/625/650/675千卡） |
| 用户心理 | 告诉 APP "我吃了几份" | 告诉 APP "我这顿吃了多少千卡" |
| 推荐机制 | 没考虑 | **推荐档 + 饱腹感说明**（"略饱,还能吃点(约七分饱)"） |
| 微调 | ±30%滑块 | "自定义热量"按钮 |

**这个份量模型的转变是整个产品最关键的设计决策：**
> 用户对"七分饱"有体感，对"200克红烧肉"没概念。让用户选绝对热量档（575/600/625/650/675千卡）而不是相对份数——推荐档中间档+饱腹感说明帮用户做决策。

### SRS 从 v1.0 → v2.0 全面校准

- 修正 30+ 处与原型不符的设计
- 重写全部 5 个页面的 ASCII 架构图
- 更新数据模型（`portion_multiplier` → `selected_calories`，加餐扩展为3个时段）
- Builder Check 子代理挑出 15 个问题，全部处理

## 第六阶段：技术决策锁定

### 4 个决策点

| # | 决策 | 用户选择 | 理由 |
|---|------|---------|------|
| A | **视觉大模型** | 通义 VL（阿里百炼） | 便宜（¥0.005/次）、中文好、适合中餐 |
| B | **食物营养数据** | MVP 手动录 50 条常用菜 | 够演示、零成本、以后扩展 |
| C | **前端框架** | React + Vite + TailwindCSS | 生态最大、Ant Design Mobile 成熟 |
| D | **MVP 存储** | Flask + SQLite | 符合用户指定的 Flask 技术栈 |

```
┌─────────────────────────────────────────┐

├─────────────────────────────────────────┤
│  后端（Flask + Python 3.11+）             │
│  ├── SQLAlchemy（ORM）                    │
│  └── SQLite（MVP 数据库）                 │
├─────────────────────────────────────────┤

└─────────────────────────────────────────┘
```
