## 一、为什么做这个（Intent & Why）

### 1.1 一句话描述

一个**以"拍照+菜单校准"为核心壁垒**的饮食热量记录 H5 应用，让食堂打饭的用户（尤其是男性）在 3 秒内完成一次不尴尬的饮食记录。

### 1.2 它要解决的三个真实痛点

| # | 痛点 | 现状 | 我们怎么解 |
|---|------|------|-----------|
| 1 | AI 拍照识别不准 | 红烧肉 → 红烧排骨 / 红烧牛肉，平均误差 30%+（NIH 2026 研究） | **有菜单时**：从今日有限菜品中匹配（准确率 85-95%） |
| 2 | 食堂打饭"拍照羞耻" | 男生在食堂对着餐盘拍照记热量，怕被同事侧目 | **偷拍式设计**：深色主题 + 3 秒完成，界面极简 |
| 3 | 手动添加太麻烦 | 搜食物 → 选份量 → 确认 → 返回（30 秒+） | **拍照优先 + 份量选热量档位**（不用算克数） |

### 1.3 用户画像（Persona）

**张小明，29 岁，某大厂产品经理**
- 天天吃公司食堂（免费且固定）
- 正在减肥，需要每日热量缺口管理
- 用过薄荷健康 / MyFitnessPal，嫌拍照不准 + 手输麻烦，3 天后卸载
- 不想在同事面前暴露"我在刻意减肥"

### 1.4 竞品对比

| 产品 | 拍照识别 | 菜单校准 | 食堂场景 | 男生羞耻感考虑 |
|------|---------|---------|---------|---------------|
| 薄荷健康 | ⭐⭐ | ❌ | ❌ | ❌ |
| CalorieMate 小卡 | ⭐⭐⭐ | ❌ | ❌ | ❌ |
| MyFitnessPal | ⭐ | ❌ | ❌ | ❌ |
| **本产品** | ⭐⭐⭐⭐（有菜单时） | ✅ | ✅ 核心场景 | ✅ 深色+极简 |

## 二、做什么 & 不做什么（Goals & Non-Goals）

### 2.1 目标（Goals）

**P0 — 必须有（MVP 可上线验证）**
- ✅ 添加食物 → 记录饮食（两种路径：搜索 / 拍照）
- ✅ 半圆仪表盘 + 总消耗/总摄入双卡片 + 热量缺口可视化
- ✅ 用餐时段建议热量区间（早餐/午餐/晚餐/加餐各有区间）
- ✅ 份量选择 = 5档绝对热量（不是相对份数），含"推荐档 + 饱腹感说明"
- ✅ 左侧垂直分类导航 + 食物图片列表 + 绿色圆形⊕添加按钮
- ✅ 拍照引导页（先说明再进相机）
- ✅ 深色主题（男生友好）
- ✅ 已记录弹窗（底部弹出，按时段分 Tab）
- ✅ 复制记录 Tab（快速复制之前吃过的）

**P1 — 菜单校准增强（差异化壁垒）**
- ✅ 用户上传食堂菜单（菜品列表文本）
- ✅ 菜单封闭匹配模式（有菜单时拍照 → 从菜单中选 → 准确率翻倍）
- ✅ 我的食堂 / 今日菜单管理

**P2 — 数据分析与建议（付费墙）**
- ✅ 今日食谱页面（会员）
- ✅ 饮食分析 / 趋势图（会员）
- ✅ 基础减肥建议（基于热量缺口）

### 2.2 非目标（Non-Goals — 本次明确不做）

- ❌ 用户账号系统（MVP 先本地存储）
- ❌ 运动消耗记录
- ❌ 体脂秤 / 智能穿戴设备对接
- ❌ 社区 / 打卡 / 社交功能
- ❌ AI 搭子聊天机器人
- ❌ 企业 B 端对接（HR 自动同步菜单）
- ❌ iOS / Android 原生 APP（本次只做 H5）

### 2.3 反目标（Anti-Goals — 做到了就算失败）

| 反目标 | 说明 |
|--------|------|
| 记录一次饮食超过 10 秒 | 如果需要打字超过 3 个字，用户就会放弃 |
| 强制用户先上传菜单才能用 APP | 菜单是**可选增强项**，没有菜单也要能正常用 |
| 界面看起来像"减肥 APP"（粉色、女生向） | 原型是深色主题，必须坚持 |
| 份量让用户算克数 | 用户不想算"吃了200克还是300克"，让他选热量档 |

## 三、技术方案（技术栈已确认的部分）

### 3.1 后端（已确定）

| 项目 | 选型 | 理由 |
|------|------|------|
| 语言 | Python 3.11+ | 用户指定 |
| 框架 | Flask | 用户指定，轻量、适合原型 |
| 数据库 | SQLite（MVP）→ PostgreSQL（规模化） | 原型阶段零运维成本 |
| API 风格 | RESTful + JSON | 前后端分离，标准协议 |

### 3.2 前端（待用户确认）

| 项目 | 推荐选型 | 理由 |
|------|---------|------|
| 框架 | React 18 + Vite | 生态最大、H5 适配成熟 |
| 样式 | TailwindCSS + 深色主题 | 原型全是深色 |
| UI 组件库 | Ant Design Mobile 5.x | 移动端组件全有 |
| 状态管理 | Zustand | 轻量 |
| 路由 | React Router v6 | |
| HTTP 客户端 | Axios | |

> ⚠️ **待用户确认**：React + Vite + TailwindCSS？还是 Vue 3 + Vite + Vant？

### 3.3 核心技术路径（两条路并存）

```
用户拍照
   │
   ├── 该用户【有上传今日食堂菜单】？
   │      │
   │      ├── YES → 菜单封闭匹配模式（准确率 85-95%）
   │      │
   │      └── NO → 通用开放式识别模式（天花板 60-70%）
   │               兜底：不准时引导手动选
   │
   └── 返回：匹配菜品列表 → 用户选中 → 5档热量选择 → 确认打卡
```

## 四、功能需求详解（v2.0 基于原型图校准）

### 4.1 页面一：首页 — 饮食记录主界面

**视觉规范：深色主题（黑/深灰背景 + 白/灰文字 + 绿色强调色）**

```
┌──────────────────────────────────┐
│ ← 返回 │ 饮食记录 │  📈趋势  │ ⋮ │  ← 顶部：返回+标题+趋势+三点菜单
├──────────────────────────────────┤
│ 🔍 请输入食物名称      📷 (绿圆)  │  ← 搜索框+绿色圆形拍照icon
├──────────────────────────────────┤
│ ◄ 2026年10月18日 ▼ ►             │  ← 日期切换器（左右箭头+日期+下拉）
│                                  │
│       ┌─────半圆仪表盘────┐       │  ← 汽车仪表盘样式（不是圆环！）
│       │ 刻度 0-800+ 红黄绿 │       │     红（缺太多）→黄（接近）→绿（达标）
│       │ 指针指向当前缺口   │       │
│       │                  │       │
│       │     891          │       │  ← 居中大号数字 = 热量缺口（千卡）
│       │   热量缺口 ⓘ     │       │     下方小字标签+信息icon
│       │    🎯 目标        │       │     仪表盘下方有"目标"按钮
│       └──────────────────┘       │
├──────────────────────────────────┤
│ 总消耗 🟠        │ 总摄入 🟢     │  ← 双卡片（不是一个数字！）
│ 891 / 2,543 千卡 │ 0 / 1,856 千卡│     已完成 / 今日目标
├──────────────────────────────────┤
│ 🥚 早餐  建议 445~650千卡  ⊕     │  ← 用餐时段卡列表
│ 🍱 午餐  建议 538~742千卡  ⊕     │     每行：emoji+名称+建议区间+绿色⊕
│ 🍗 晚餐  建议 501~668千卡  ⊕     │     不是Tab！是独立卡片垂直堆叠
│ 🍎 加餐  建议 0~278千卡    ⊕     │
├──────────────────────────────────┤
│ 🍱 今日食谱 会员 │ 📊 饮食分析 会员 │  ← 底部TabBar，**两个都标"会员"**
└──────────────────────────────────┘
```

**数据计算：**
- 总消耗建议上限 = Mifflin-St Jeor(BMR) × 活动系数
- 总摄入上限 = 总消耗建议上限 - 热量缺口目标（如减脂 -300）
- 热量缺口 = 总消耗建议 - 已摄入（仪表盘大数字）
- 每个用餐时段建议区间 = 总摄入上限 × 分配比例 ± 浮动（如早餐 25-35%、午餐 30-40%、晚餐 25-35%、加餐 0-15%）
- 日期切换：左右箭头切前后日期，下拉直接选日期

**⚠️ 与v1.0的关键差异：**
- 仪表盘是半圆（不是圆环），带刻度和指针
- 双卡片：总消耗 + 总摄入（不是一个"热量缺口"数字行）
- 每个时段有**区间值**（如 445~650），不是固定值
- 底部TabBar标了"会员"——这是 P2 付费墙
- 深色主题（原型全程深色）

### 4.5 页面五：份量/热量选择弹窗（最核心的设计）

```
┌──────────────────────────────────┐
│ ← 10/18              快速录入 🟢  │
├──────────────────────────────────┤
│ 午餐 10:56 ▼                     │
├──────────────────────────────────┤
│                                  │
│  ┌─ 午餐 10:56 ▼ ───────── ✕ ┐   │  ← 底部弹出模态框
│  │                           │   │
│  │          575 千卡         │   │
│  │          600 千卡         │   │
│  │     625 千卡 🟢推荐       │   │  ← 5档绝对热量（不是份数倍率！）
│  │   略饱,还能吃点(约七分饱)  │   │     中间档=推荐，带饱腹感说明
│  │          650 千卡         │   │
│  │          675 千卡         │   │
│  │                           │   │
│  │  [自定义热量]  [确认打卡🟢]│   │  ← 底部：自定义+确认
│  └───────────────────────────┘   │
├──────────────────────────────────┤
│ 🍽️已记录 │  完成打卡 🟢  │  📷   │
└──────────────────────────────────┘
```

**🔥 这是整个产品最关键的设计决策，我v1.0完全理解错了！**

| v1.0 SRS（我的误解） | 原型真实设计 |
|---------------------|-------------|
| 小份/中份/大份（0.5x/1.0x/1.5x） | **5档绝对热量值**（575/600/625/650/675千卡） |
| 用户换算"我吃了多少克" | 用户直接选"我这顿吃多少千卡" |
| AI估算份量→算热量 | **产品内置饱腹感指导**：625千卡=七分饱=推荐 |
| 微调±30%滑块 | "自定义热量"按钮 |

**产品哲学转变：**
> 不是让用户告诉APP"我吃了几份红烧肉"，而是让用户告诉APP"我这顿大概吃了多少千卡"——**用户对"七分饱"有体感，对"200克红烧肉"没概念**。推荐档帮用户做决策，"略饱,还能吃点(约七分饱)"比"标准份"更有温度。

**热量档位计算逻辑（需后端实现）：**
1. 用户选中食物列表（如：红烧肉+米饭+清炒时蔬）
2. 后端根据食物标准份量计算出"这顿全部吃标准份"= X 千卡
3. 以 X 为中心，生成 5 档：X-50, X-25, X(推荐), X+25, X+50
4. 标注推荐档的饱腹感：略饱(七分饱)/ 刚好(八分饱)/ 很饱(十分饱)

## 八、风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| VLM 在真实餐盘照片上准确率不如预期 | 高 | 核心壁垒不成立 | Spike 先验证，不过关就调 Prompt 或换模型 |
